# Personal Remote Desktop Protocol v1

## 1. Scope

This document defines the application framing and session state machine shared by
the macOS controller and Windows agent. Version 1 uses a reliable ordered byte
stream (TLS over TCP). Tailscale supplies device reachability and network-layer
encryption, but it does not replace application authentication.

The first video transport is JPEG. H.264 message types are reserved so that the
framing does not need to change later.

## 2. Conventions and limits

- Every integer is unsigned and encoded in network byte order (big-endian).
- Sizes are measured in bytes.
- Text is UTF-8 without a byte-order mark.
- The fixed v1 header is 28 bytes.
- A payload may be at most 8 MiB (`8,388,608` bytes).
- Control payloads may be at most 64 KiB (`65,536` bytes).
- A peer must reject a frame before allocating its payload when a declared size
  exceeds the applicable limit.
- Secret material, authentication payloads, screen frames, and key events must
  never be written to logs.

Implementations may choose a smaller negotiated video-frame limit, but never a
larger one without a future protocol version.

## 3. Frame format

| Offset | Size | Field | v1 value / meaning |
|---:|---:|---|---|
| 0 | 4 | magic | ASCII `PRD1` (`50 52 44 31`) |
| 4 | 2 | version | `1` |
| 6 | 2 | header length | `28` |
| 8 | 2 | message type | See section 4 |
| 10 | 2 | flags | Must be `0` in v1 |
| 12 | 4 | payload length | `0...8,388,608` |
| 16 | 4 | sequence | Per-direction counter, starting at `1` |
| 20 | 8 | timestamp | Monotonic microseconds; `0` if not applicable |
| 28 | N | payload | Message-specific bytes |

Sequence counters are independent in each direction. They wrap from
`0xffffffff` to `1`; zero is reserved for frames that do not participate in a
session. A receiver must preserve frame boundaries across arbitrary stream
splits and coalescing.

Unknown message types, non-zero reserved flags, unsupported versions, invalid
header lengths, and oversized payloads are protocol errors. The receiver should
send `ERROR` when safe, then close the session.

## 4. Message types

| Value | Name | Direction | Authentication required |
|---:|---|---|---|
| `0x0001` | `HELLO` | Both | No |
| `0x0002` | `AUTH_CHALLENGE` | Agent to controller | No |
| `0x0003` | `AUTH_RESPONSE` | Controller to agent | No |
| `0x0004` | `AUTH_RESULT` | Agent to controller | No |
| `0x0005` | `SCREEN_INFO` | Agent to controller | Yes |
| `0x0006` | `VIDEO_FRAME_JPEG` | Agent to controller | Yes |
| `0x0007` | `VIDEO_FRAME_H264` | Agent to controller | Yes; reserved |
| `0x0008` | `MOUSE_MOVE` | Controller to agent | Yes |
| `0x0009` | `MOUSE_BUTTON` | Controller to agent | Yes |
| `0x000a` | `MOUSE_WHEEL` | Controller to agent | Yes |
| `0x000b` | `KEY_EVENT` | Controller to agent | Yes |
| `0x000c` | `PING` | Both | Yes |
| `0x000d` | `PONG` | Both | Yes |
| `0x000e` | `DISCONNECT` | Both | No |
| `0x000f` | `ERROR` | Both | No |

Input messages are defined now but must not be acted upon until the input phase
of the product is implemented and the session is authenticated.

## 5. Handshake payloads

### 5.1 `HELLO` (41 bytes)

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | Role: `1` controller, `2` agent |
| 1 | 2 | Minimum supported protocol version |
| 3 | 2 | Maximum supported protocol version |
| 5 | 4 | Capability bitset |
| 9 | 32 | Random hello nonce |

Capability bits: bit 0 JPEG, bit 1 H.264, bit 2 input, bit 3 reconnect.
Unknown bits are ignored. Each hello nonce must come from a cryptographically
secure random generator and must not repeat.

### 5.2 `AUTH_CHALLENGE` (48 bytes)

- Bytes 0...31: cryptographically random challenge.
- Bytes 32...47: stable 16-byte agent identifier, which is not a secret.

### 5.3 `AUTH_RESPONSE` (32 bytes)

The response is:

```text
HMAC-SHA256(
  deviceKey,
  ASCII("PRD-AUTH-V1") ||
  controllerHelloNonce ||
  agentHelloNonce ||
  challenge ||
  agentIdentifier
)
```

`deviceKey` is 32 random bytes generated by the agent. It is provisioned out of
band and stored in Keychain on macOS and an OS-protected store on Windows. The
agent compares the response in constant time. A challenge is single-use.

### 5.4 `AUTH_RESULT`

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | Result: `0` success, `1` rejected, `2` temporarily locked |
| 1 | 4 | Retry delay in milliseconds; zero on success |

Authentication failures must be rate-limited. The initial implementation uses
an increasing delay and caps it at 30 seconds. A new transport connection must
perform a complete handshake with fresh nonces; authentication responses and
session state are never reusable.

## 6. Authenticated payloads

### 6.1 `SCREEN_INFO` (18 bytes)

| Offset | Size | Field |
|---:|---:|---|
| 0 | 4 | Physical pixel width |
| 4 | 4 | Physical pixel height |
| 8 | 4 | Horizontal DPI multiplied by 100 |
| 12 | 4 | Vertical DPI multiplied by 100 |
| 16 | 1 | Pixel format: `1` BGRA8 |
| 17 | 1 | Display index; v1 must be `0` |

### 6.2 `VIDEO_FRAME_JPEG`

The entire payload is one complete JPEG image. A receiver validates the payload
length before allocation and discards undecodable images without losing the
next frame boundary. The controller retains at most the newest complete frame.

### 6.3 Input messages

- `MOUSE_MOVE`: two unsigned 16-bit normalized coordinates (`0...65535`).
- `MOUSE_BUTTON`: button byte (`1` left, `2` right, `3` middle), followed by an
  action byte (`1` down, `2` up).
- `MOUSE_WHEEL`: signed 32-bit horizontal delta followed by signed 32-bit
  vertical delta, encoded as big-endian two's-complement values.
- `KEY_EVENT`: unsigned 16-bit Windows scan code, one extended-key byte
  (`0`/`1`), and one action byte (`1` down, `2` up).

Coordinates are normalized against the remote physical screen. The controller
must ignore clicks in letterbox regions and clamp coordinates before encoding.

### 6.4 Heartbeat

`PING` contains an opaque 8-byte identifier. `PONG` echoes it unchanged. A peer
may declare the connection dead after three expected heartbeat intervals with
no valid traffic. Exact intervals are an implementation policy, not wire data.

### 6.5 `DISCONNECT`

The payload begins with an unsigned 16-bit reason code and may contain up to 256
bytes of diagnostic UTF-8 text. Diagnostic text must not contain secrets.

## 7. Error codes

`ERROR` begins with a 16-bit code, followed by up to 256 bytes of safe UTF-8
diagnostic text.

| Code | Name | Meaning |
|---:|---|---|
| 1 | `MALFORMED_FRAME` | Invalid magic, length, flags, or payload |
| 2 | `UNSUPPORTED_VERSION` | No mutually supported protocol version |
| 3 | `UNSUPPORTED_MESSAGE` | Message type is unknown or unavailable |
| 4 | `AUTH_REQUIRED` | Authenticated-only message arrived too early |
| 5 | `AUTH_FAILED` | Authentication response was rejected |
| 6 | `SESSION_BUSY` | Another controller owns the active session |
| 7 | `MESSAGE_TOO_LARGE` | Declared payload exceeds its limit |
| 8 | `INVALID_STATE` | Message is invalid in the current state |
| 9 | `INTERNAL_ERROR` | Non-sensitive internal failure |

## 8. Session state machine

```text
Disconnected
    -> Connecting (controller only)
    -> AwaitingHello
    -> Authenticating
    -> Authenticated
    -> Closing
    -> Disconnected
```

Both peers send `HELLO` immediately after the TLS stream is ready. The agent
sends `AUTH_CHALLENGE` only after compatible hellos are exchanged. Only the
challenge/response messages, `DISCONNECT`, and `ERROR` are accepted while
authenticating. Screen, video, heartbeat, and input messages are accepted only
after a successful `AUTH_RESULT`.

The agent permits one authenticated controller at a time. A second connection
receives `SESSION_BUSY` and is closed. User-initiated disconnect does not
silently reconnect; network failures may use capped exponential backoff and
must repeat the entire handshake.

## 9. Transport security

Production sessions require TLS. P3 will define certificate creation, first-use
trust, and certificate fingerprint pinning. Until that implementation exists,
all skeleton code is test-only and must not expose a listening port. Tailscale
addresses alone are not an authentication decision.

## 10. Golden vectors

`protocol/testdata/v1.json` is the cross-language source of truth for framing
tests. Frames are stored as hexadecimal text so they remain reviewable in Git;
tests decode the text to the exact wire bytes before parsing. Any framing change
must update this document, both language implementations, and these vectors in
the same change.
