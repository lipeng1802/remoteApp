# 设备码与一次性邀请授权核心

## 2026-10-07 私有受控注册后端核心

新增 `ProvisionBackend` 及持久化注册账本，复用现有单写者快照/原子提交；旧快照没有账本字段也可读取，已有公钥/设备码不重置。本轮是核心与驱动契约，**尚无真实 Headscale 驱动、动态 ACL 实机或 helper 注册接入**，不开放 HTTP 注册接口，不改服务器/产品/系统 Tailscale。内存驱动测试不证明网络节点持有验证已实现。

读取兼容是新程序读取旧快照；新增账本的快照不应交给旧版本严格解码器，不删除字段或重置身份来强行降级。回退须保留匹配版本与快照备份。策略就绪状态共享到 Store，任何管理 wrapper 的同步失败都会阻止其他 wrapper 发钥匙。

设备签名独立域的注册意图，覆盖 grant ID、预期节点公钥、nonce、时间；必须拥有当前批准授权的一方身份。先保存随机工单和预期身份，再调用驱动发单次凭据，期限为当前时间加 120 秒与 grant 到期的较早者。凭据仅一次返回，不落盘/不日志化；快照只保存工单与 provider handles。相同设备/节点尚未回收时拒绝新发钥匙，nonce 跨重启防重放，账本最多 512 条、状态总量仍限 1 MiB。

状态 `planned → issued → bound`；异常/回收为 `cleanup_pending → cleaned`。节点观察必须与工单用户/预期节点公钥一致，且由可信驱动独立完成真实网络持有挑战验证后才能绑定；用户提交的 IP/公钥/verified 布尔不能当证明。仅同一个真实有效 grant 的目标和控制端均绑定，才生成控制端 IP→目标 IP:47476 的单向最小规则；没有通配符。注册 key 到期不能撤销已绑定且仍有效的会话。

启动时先 `Reconcile`，成功后才发凭据；同 Store 的特权驱动调用串行化。注册意图先落盘，Mint 结果不明或崩溃遗留计划只按准确工单发现和回收外部资源，不重试 Mint，避免重复私钥/节点。先投影当前规则撤回无效授权，再做精确回收、持久记录确认，最终重算规则；清理失败保留 pending，下次重试。策略失败禁止继续发凭据。驱动不可用时不能保证外部旧 ACL 已撤回，仍必须保留现有签名状态/应用门禁限制，不把错误返回当作网络已拒绝。

`ProvisionDriver` 是私有特权契约：单次短期 Mint、可信 Observe、独立 Verify、按工单幂等/精确 Cleanup、仅替换本后端管理策略的原子 ReplaceRules。真正驱动必须响应 5 秒 context 截止；核心不会强杀忽略取消的驱动。Provider/Store 在后端运行期间保持固定，退出须先停止并等待请求，再关闭 Store。正式部署仍需最小管理权限、证据验证、策略多租户/并发收敛、防滥用、受控秘密投递及恢复策略。

零条规则必须落实为显式 deny-all，不能省略策略、序列化为隐含默认或回退到默认允许；真实驱动需用未授权节点实测这一点。

新增测试涵盖最小策略、无密钥明文持久化、重启/注册 key 与 grant 到期区别、重复/重放/第三身份、Mint 未知结果与 crash 恢复、观察/持有验证门禁、撤销先撤规则/回收失败重试、策略失败禁发凭据、并发只发一次、意图篡改/时间/大小、时钟回退和损坏账本。执行全量 `go test -race ./...`，原邀请/会话测试仍独立保留。下一切片做 Headscale 受限驱动及双机实际注册/策略回收，不修改原公共业务策略。

这是独立 PoC 后端，不是已上线的免账号远控产品。没有接入 Headscale 注册/ACL、真实 helper 授权检查、产品 TLS 或键鼠，也没有公网接口。

## 已实现的流程

1. 设备持有 Ed25519 私钥，签名注册自己的公钥。设备身份为公钥 SHA-256，服务分配稳定的 12 位十六进制设备码；重启不改变身份或设备码。
2. 被控端签名创建邀请，收到一次显示的 8 位数字验证码，120 秒有效。新邀请替换该设备上一邀请，并拒绝其未批准请求。
3. 控制端只提交被控设备码和验证码，不需手工输入内部邀请 ID；兑换成功只产生 pending。邀请原子消费，并发最多一位控制端成功。
4. 被控端签名确认/拒绝请求；其他设备不得批准或查询。明确批准后才签发 300 秒授权，绑定目标/控制端应用公钥身份、固定载荷权限、时间与随机 grant ID；一个被控设备最多一个有效授权。
5. 控制端可轮询自己请求的状态。被控端或该控制端可撤销授权；撤销/拒绝/已消费邀请、请求 nonce 和限速预算写入私有状态，重启不复活旧权限。

所有操作请求签名包含 action、完整字段、时间及 128 位随机 nonce，并有独立协议域；请求时间窗口 ±30 秒。有效签名的失败操作也消费 nonce、记录限速，不因拒绝或重启丢失预算。每位控制端和每个当前邀请每 60 秒最多 5 次兑换尝试，未知目标/错误验证码/不匹配邀请统一拒绝。验证码只保存服务密钥派生的 HMAC，不保存明文；不是长期认证密钥，也不派生已有产品密钥。

授权签名校验必须使用预先信任的服务公钥。`VerifyGrant` 仅验证签名/绑定/到期；**不代表授权未撤销**。`Store.Authorized` 还检查当前持久化授权状态。后续桥接必须查在线授权或使用有界有效期的撤销通知机制；不能单凭离线签名继续控制。

## 运行与验证

在仓库根目录使用隔离 Go 工具链，示例（缓存已准备，不下载依赖）：

```bash
GOENV=off GOTOOLCHAIN=local GOPROXY=off \
GOMODCACHE="$PWD/artifacts/connection-poc/gomod" \
GOCACHE="$PWD/artifacts/connection-poc/gocache" \
artifacts/connection-poc/toolchain/go/bin/go -C poc/selfhost test -race ./invite
```

同一环境执行 `go -C poc/selfhost run ./cmd/invite-api` 启动固定 `127.0.0.1:18445`；不接受改为公网监听的参数。私有状态放在工作区忽略的 `artifacts/connection-poc/invitation`。Unix 平台上的目录要求 0700、快照/lease 文件 0600；客户端签名逻辑平台无关，不宣称后端 Windows 持久化实机支持已完成。

HTTP 入口：`GET /health`、`POST /v1/request`。POST 仅接受 application/json 的签名 Envelope，最大 4096 字节，拒绝未知字段、尾随 JSON、query、Origin 和其他方法/路径；不启用 CORS，不记录请求/验证码/授权。响应 no-store。真正应用客户端会用设备私钥调用 `invite.Sign`，不是让最终用户手工拼 JSON。

本机实测包括真实 loopback HTTP 创建→申请→确认→状态→重启→撤销→再次重启，配合核心身份/签名/绑定、拒绝、到期、重放、并发抢兑、重启后限速、单活动授权、结果副本隔离、私有权限、存储损坏/丢失和提交失败时停止授权。单测及竞态检查通过。现有 verify.zsh 依赖/单测/本机自建 DERP 回归通过。Linux x64 后端命令交叉构建通过，不代替 Linux 实机部署验收。

## 持久化与边界

单进程 mutex + 独占 writer.lock 防止第二写者。快照采用私有临时文件、文件 fsync、原子 rename、目录 fsync；提交失败后本实例停止授权，不返回成功。已有目录缺失/损坏快照时拒绝启动，不静默生成新的服务身份。异常退出遗留 lease 时也拒绝自动接管；需要操作员确认旧进程停止并核对快照后人工恢复，不自动删锁/重置数据库。

当前最多 128 个设备、512 个邀请、512 个请求、4096 个近期 nonce、1024 个限速桶；快照 1 MiB。已使用/撤销记录保留，配额耗尽拒绝新操作，尚无生产归档/压缩或多进程数据库方案。设备私钥生命周期/平台安全存储尚未接产品。

此签名证明设备持有私钥，不证明注册者是“可信用户”。loopback 不是完整安全边界；公网发布前必须实现入口滥用防护/注册配额、HTTPS、可信服务公钥分发、设备通知/轮询与恢复策略、Headscale 节点身份绑定/注册下发/动态网络策略，以及活动流撤销的端到端闭环。本轮没有修改服务器、Nginx、Tailscale、真实凭据或安装包。
